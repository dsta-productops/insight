## Step 5 — end-of-session transcript view/export (✅ done)

All three pieces shipped, all keyless/local by default:

1. **Post-session speaker labeling** — `lib/transcribe/label.ts` runs one LLM pass over the finished transcript, labeling each segment `researcher`/`participant` (question-vs-answer structure is strong signal). This is the deferred diarization answer. Uses the same provider selection as the coach (`SUGGEST_PROVIDER`, local Ollama `llama3.1:8b` default; temp 0, `num_predict: 2048`). Endpoint `POST /api/sessions/[id]/label` persists `speaker` onto segments + a `labeledAt` stamp; idempotent (re-label recomputes). Segments the model doesn't label stay `undefined` — never guessed.
2. **Session detail review** (`/sessions/[id]`) — the transcript renders with speaker labels, and every logged coach cue is **anchored inline by time** (offset = suggestion `at` − transcript `createdAt`, clamped to the transcript span) so the reviewer sees what surfaced *and when*. Header has Label/Re-label + Markdown + JSON actions. `GET /api/sessions/[id]` now also returns the suggestion log. All PRIZM primitives (Card/Badge/Button/Text), semantic tokens only.
3. **Structured export** — `lib/export/session.ts` builds a CLARA-friendly JSON (`session` + labeled `transcript` + flattened, time-anchored `coachActivity`) and a readable Markdown (metadata, speaker-labeled transcript with timestamps, coach-activity section). `GET /api/sessions/[id]/export?format=json|md` returns a file download. **Do NOT build the CLARA integration** — just keep the shapes clean.

Everything above is keyless/local — keep it that way. **The product's five-step brief is now complete.**

## Session refinements (2026-07-25)

A second polish session. Still no changes to the coach logic or the local/keyless stack; all data-layer changes preserve the JSON-file store shapes.

**Multi-select delete correctness fix (sessions) + hardening (documents)**
- **The bug:** `DELETE /api/sessions` ran `Promise.all(ids.map(removeSession))`. Each `removeSession` did its own read-modify-write of `data/sessions.json`, so concurrent deletes all started from the same snapshot and the **last write clobbered the rest** — only one of N selected sessions actually got removed, though the response reported `removed: N`. That was the "multi-delete doesn't delete correctly" report.
- **Fix:** new `removeSessions(ids)` in `lib/transcribe/sessions.ts` does a **single atomic read-filter-write** for the whole batch, then per-id file cleanup. Route calls it once. Same pattern added to documents as `removeDocuments(ids)` in `lib/rag/store.ts` (documents was already race-free via a sequential `for await`, but batching hardens it against a future refactor and is more efficient). The old singular `removeSession`/`removeDocument` wrappers were removed.
- **Leak fixed:** session delete now also removes `data/suggestions/<id>.json` (new `removeSuggestionLog` in `lib/suggest/log.ts`) — previously only the transcript + audio were cleaned, so suggestion logs orphaned on every delete. Cleaned up ~48 pre-existing orphaned transcript/suggestion files (moved to a scratchpad backup, not hard-deleted).
- **Latent hazard, still open:** the JSON-file store is inherently vulnerable to this read-during-write race. There's a pre-existing intermittent `JSON.parse: Unexpected end of JSON input` on `/api/documents` when a read lands mid-write (readStore swallows its own parse error and returns EMPTY, but a concurrent request elsewhere can 500). Not fixed this session — worth hardening readStore/readSessions with atomic temp-file writes + retry-on-read if it resurfaces.

**DMG build gotcha — RESOLVED 2026-07-30 (`.dmg` now builds).** First `npm run tauri:build` failed at `bundle_dmg.sh` with the generic `error running bundle_dmg.sh … exit 64`. Root cause: `bundle_dmg.sh` runs a **Finder AppleScript** (`osascript`, via `tell application "Finder"`) to prettify the DMG window; that `osascript` fails when the terminal lacks macOS **Automation permission to control Finder** (or hits a transient "Can't get disk (-1728)"), and the script then does `exit 64`. Fingerprint: a leftover mounted `/Volumes/dmg.XXXXXX` volume + an orphaned multi-GB `rw.*.dmg` in `bundle/macos/`. **Fix: build with `CI=true`** — tauri-cli (2.11.4) then passes `--skip-jenkins` to `bundle_dmg.sh`, skipping the cosmetic AppleScript and producing a plain, fully functional DMG (no custom drag-to-Applications background — irrelevant for an internal/demo build). Verified: produced `INSIGHT_0.1.0_aarch64.dmg` (~5.1 GB, Apple silicon) + `INSIGHT.app`, no leftover temp image/volume. ## Session (2026-07-31) — running conversation summary (the "catch-up" feature)

Alvin wanted an **active/ongoing summary** that highlights what's been covered as an interview progresses, so the researcher can glance and re-sync if they miss part of the conversation. We discussed it at length first and locked the framing before building.

**What it is (and deliberately isn't).** It's a **catch-up recap**, not findings synthesis. The job-to-be-done is "I glanced away / was forming my next question and lost the thread — let me re-sync in two seconds." So it reports *what was said* (factual, extractive), it does NOT interpret or advise — that's the coach's job. This framing is what makes it safe on the local 8B: recap is close to extraction (well within the 8B's range), whereas open-ended synthesis is exactly what the model is bad at. Do NOT let this drift into a "key insights / findings" generator without re-testing quality.

**Design decisions (locked with Alvin):**
- **Pull, not push.** The coach's Now card is the one actionable push. The summary is a reference you consult when lost — it must never compete with the Now card for attention. It lives on the RIGHT (transcript) column of `/live` — the "what was said" axis — above the transcript. The LEFT coach column is untouched/calm.
- **Incremental, bounded cost.** Each pass folds ONLY the newest transcript window into the existing bullets (never re-summarizes the whole transcript), so a pass stays ~3.5s regardless of interview length. Capped at 6 glanceable bullets; the merge drops/combines older points to stay tight.
- **Hide = pause compute.** The panel has a Hide/Show toggle; hidden also stops the loop entirely (zero GPU cost when unwanted). Default shown.
- **Low cadence + yields to the coach.** `SUMMARY_INTERVAL_MS = 45000` (vs the coach's 8s). At fire time it skips if a coach pass is in flight (`suggestInFlight`), so it never contends a nudge on the shared GPU.

**Performance — measured on Alvin's machine before building (bundled 8B, `-c 4096`, the exact packaged config).** The shipped `llama-server` runs 4 slots (llama.cpp default; the app passes no `-np`), so a coach pass and a summary pass batch together rather than one hard-blocking the other — but they share one GPU, so overlap ~halves throughput. Numbers: coach alone **2.7s**; summary alone **3.5s**; coach *while a summary runs concurrently* **5.4s (+2.7s, ~2×)**. Conclusion: un-scheduled it would ~double coach latency during overlaps, but the coach is idle ~5.3s of every 8s, and a 3.5s summary fits that idle window — so with yield-to-coach + low cadence the realized coach hit is ~zero. (Caveat: the bench is coach-vs-summary only; live also has Whisper on the GPU, shrinking the idle gap somewhat — +2.7s is the ceiling for coach-vs-summary, not the three-way. Confirm the felt latency on a real recording.) Bench script + `bench.py` are in the session scratchpad.

**What was built (all keyless/local by default, mirrors existing patterns):**
- `lib/summary/index.ts` — engine, mirrors `lib/transcribe/label.ts`'s 4-provider abstraction (ollama/llamacpp/anthropic/groq), grammar-enforced `json_schema`. `updateSummary(bullets, window)` (one incremental merge) + `summarizeTranscript(segments)` (full regen by folding REGEN_WINDOW=12-segment windows). ## Session (2026-07-31, part 8) — keep-awake during recording + live/review suggestion parity

**Keep the Mac awake while recording (new).** A live interview could be cut short if the machine idle-sleeps (mic + coach stop). **`lib/keep-awake.ts`** spawns the macOS system `caffeinate` while a session is live: `preventSleep()` on session start (`POST /api/sessions/live`), `allowSleep()` on end (`PATCH /api/sessions/live/[id]`). ## Distribution / packaging — the strategic open decision (discussed 2026-07-25, no code yet) — SUPERSEDED, see the 2026-07-28 section above

Alvin asked what's left to ship this as a standalone Mac app, then explored alternatives. **No packaging exists** (`src-tauri` absent, `build` is plain `next build`). Nothing was built — this is the decision to make next. Three paths surfaced; the deciding question is **where the compute runs**, which turns on **desk-on-network vs field-disconnected** use:

- **Option A — internal on-prem server, users open a URL in a browser.** Zero install, zero packaging, best UX, always current; data stays on the internal network (on-prem ≠ cloud, so it likely satisfies the offline/defense requirement in `insight-offline-value-prop.md`). **Heavy compute runs on the server, not each laptop**, so a weak *local network* (note: not "internet") only slightly delays live text + the end-of-session audio save (~100 MB/hr) — the AI/transcription speed is unaffected. **Catch:** needs a network to that server; no good for truly disconnected/field use.
- **Option B — run entirely in the browser (WASM + WebGPU).** Whisper-in-WASM + an in-browser LLM (WebLLM/WebGPU) + browser storage (IndexedDB/OPFS); big one-time model download cached for offline use after. Zero install, no Apple signing, data never leaves the machine — cleanest fit for "seamless + private". **Catch:** significant re-architecture (server logic → client), comparable effort to the Mac app; leans on the user's GPU (slower on weak machines); needs a modern browser (Chrome/Edge safe, Safari historically lagged on WebGPU).
- **Option C — the Mac app (Tauri), or a lighter double-click launcher.** Fully offline on any machine, works in the field. **Catch:** most build effort + Apple code-signing/notarization (needs an Apple Developer account — an infra decision Alvin can't own; flag it).

If we go **C (Tauri)**, the load-bearing work (from a grounded pass): a **Node/Next sidecar** (Tauri won't run the server for you), **how the coach LLM ships** (require Ollama separately / bundle llama.cpp+GGUF / smaller model — recommend bundle llama.cpp; `llama3.1:8b` is the quality floor per this file), **relocate all `data/` paths** (everything is `process.cwd()+"data"` today — breaks in a bundle; move to `~/Library/Application Support/INSIGHT`, split read-only bundled assets from writable user data), **bundle whisper-cli + the model**, **mic entitlement** (Info.plist `NSMicrophoneUsageDescription`), and first-run/startup orchestration. Recommended first step regardless of path: the **data-path relocation** — pure, decision-free engineering everything else depends on.

**Coach-model swap (asked, not started):** if a more capable LLM is dropped in later, retuning needed is mostly *removing crutches* — the rigid technique-decision-order + anti-repeat exist to babysit the 8B and can likely relax (a strong model may do worse in that straitjacket); re-time the 8 s throttle to the new model's speed; and a **cloud/paid model breaks the free/offline promise** (a stronger *local* model keeps it).
